# Threat model (updated, Phase 5)

Scope: PRD §11. Review this at the end of every phase. Status is either **mitigated** (implemented and tested), **partial**, or **planned** (with the phase).

| # | Threat | Impact | Mitigation | Status |
|---|---|---|---|---|
| T1 | Cross-client or cross-organization record access by guessing IDs | Data exposure (release blocker) | RLS on every table, record-level policies, UUID keys, tests in `tests/security/rls.test.ts` | Mitigated for Phase 1–4 tables (`rls.test.ts`, `phase2.test.ts` to `phase4.test.ts`) |
| T2 | Role escalation (self-promotion, editing `role_permissions`) | Full compromise | No client write grants on memberships or permissions; audited RPC requires `members.manage` and blocks self-changes | Mitigated |
| T3 | Trusting client-supplied role, status or ownership | Privilege bypass | Server derives context from the verified JWT and the database; RPCs re-check | Mitigated |
| T4 | Tampering with the audit trail | Loss of accountability | Append-only triggers on update, delete and truncate; service role also revoked; no client inserts | Mitigated |
| T5 | Account enumeration through sign-in | Reconnaissance | Same response whether or not the email exists; signup disabled; `shouldCreateUser: false` | Mitigated |
| T6 | Open redirect through `?next=` | Phishing | `safeRedirectPath` allows same-origin relative paths only | Mitigated |
| T7 | Secret leakage (keys in the browser, logs or the repo) | Full compromise | Secret key used server-side only, for system steps (D-008, D-012); `.env*` gitignored; structured logger redacts sensitive keys; error envelope hides internals | Partial: secret scanning in CI planned for Phase 6 |
| T8 | Session theft / CSRF | Account takeover | Supabase httpOnly cookies, Next.js server action origin checks, sign-out is POST only, `X-Frame-Options: DENY` | Partial: nonce-based CSP planned once providers are chosen |
| T9 | Weak internal authentication | Account takeover | Magic links (single use, one-hour expiry) | Partial: MFA (TOTP) for internal users planned before the pilot (Phase 6) |
| T10 | Invitation theft or forwarding | Unauthorized proposal access | 256-bit tokens stored only as hashes; scoped to one prospect/proposal; 1–30 day expiry; immediate revocation and replacement; accepting requires a verified magic link to the invited email, and redemption is bound to it; redeemed links stop working without sign-in; `Referrer-Policy: no-referrer` on invitation pages | Mitigated (AT-001 to AT-004). Residual risk: someone who receives a forwarded link can *read* the proposal until it expires or is revoked. Accepted by the PRD ("invite link grants limited initial access") |
| T11 | Webhook spoofing, replay or payment-state manipulation | Financial loss | HMAC verification of the raw body in the app (secret server-side); unverified events stored quarantined with no data and never replayable; only verified events claim a provider event ID (a forgery cannot pre-empt the real event); dedupe on event ID and on refund/dispute IDs; order, amount, currency and merchant account must match; provider enabled per organization; ingest is service-role only; evidence rows immutable even to the service role; the browser return page never marks anything paid | Mitigated (AT-014 to AT-020, `phase3-rules.test.ts`, `phase3.test.ts`, `integrations.test.ts`). Residual: forged events consume storage until edge rate limiting is in place (D-009) |
| T12 | Malicious or oversized file uploads | Malware, data exposure | 10 MB cap; allow-list of types with matching extension and content signature (SVG/HTML refused); storage path never derived from the filename; private bucket with no storage policies; downloads authorized, audited and served by 60-second signed URLs; same-origin check on the upload route | Partial (AT-022 tested): no malware scanner yet, so assets are marked `not_scanned`; add scanning before accepting files from untrusted senders at scale |
| T13 | Prompt injection or cross-client leakage through AI | Data exposure, false commitments | Context built only from the caller's authorized projections (other clients' data is never in the prompt); context marked as data; output policy: citations must reference supplied items, figures must appear in cited items, identifiers and emails absent from context are refused, client-facing promises (discounts, guarantees, payment/signature/activation claims) are refused; no model-callable tools, so actions are proposals a person confirms; per-person and per-organization daily budgets; evaluation set with injection and leakage cases | Mitigated (AT-027 to AT-030: `ai.test.ts`, `phase5-rules.test.ts`, `phase5.test.ts`). Re-run `npm run ai:eval` with the chosen vendor before launch |
| T14 | Brute-forcing or flooding public token endpoints | Data exposure, noise in follow-up queues | Infeasible to guess tokens (2^256); malformed tokens are rejected before any DB call; help requests are capped at 2,000 characters and never reveal whether a token exists | Partial: per-IP rate limiting is to be enforced at the hosting edge (Vercel Firewall or equivalent) before the pilot (D-009) |
| T15 | Tampering with prices, totals or accepted terms | Financial and legal loss | Line amounts are derived in SQL (client totals ignored); submitted versions and line items are immutable via triggers; acceptance checks the version ID and SHA-256 terms hash; acceptance is audited as `client` | Mitigated (AT-005 to AT-007) |
| T17 | Sandbox provider left enabled in production | Clients could simulate payments and signatures | Two independent switches: `ENABLE_SANDBOX_PROVIDERS` (also forced off when `VERCEL_ENV=production`) and an active `sandbox` integration account for the organization; neither exists in production (D-013) | Mitigated by configuration; add a deploy check in Phase 6 |
| T18 | Double booking or calendar manipulation | Lost meetings, poor client experience | Postgres exclusion constraint on host + time range; idempotency keys; routing and host purposes only changeable with `scheduling.configure`; clients read meetings only through projections | Mitigated (AT-010, concurrent test on hosted Postgres) |
| T19 | Agreement terms diverge from the accepted proposal, or are edited after signing | Legal dispute | Agreement rendered in SQL from the exact accepted version; checksum and template hash stored; content frozen at ready-to-send by trigger; executed agreements cannot change state; amendments are new linked records; signing re-checks the checksum the signer saw | Mitigated (AT-012, AT-013) |
| T20 | Delivery staff overreach (other clients, commercial or financial data) | Data exposure | Access only through workspace assignment; no CRM, proposal, agreement or invoice grants; onboarding material only after approval; tested with assigned and unassigned delivery users | Mitigated (AT-023, AT-024) |
| T21 | Clients handing over passwords through the portal | Credential exposure | Access grants track platform delegation only; text that looks like a password is refused in instructions and client notes | Mitigated (best effort pattern check) |
| T16 | Unapproved or withdrawn testimonials shown to prospects | Misleading claims, consent breach | Visibility is computed on every read (status, withdrawal, permission expiry, channel); approval requires source and permission evidence; metrics require period and evidence | Mitigated (AT-009) |
